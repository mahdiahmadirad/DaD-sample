# ADR-0001: Keep text-analysis providers replaceable

## Status

Accepted

## Context

The sample needs an implementation of text analysis, beginning with summarization. A direct integration with a vendor SDK would be the shortest path to a working endpoint, but it would also make feature code depend on a provider choice that is not part of the product behavior.

Provider independence is useful here for two reasons. First, it is a realistic architectural decision whose rationale cannot be reconstructed reliably from an interface alone. Second, it gives the DaD sample a durable constraint that later changes can preserve, challenge, or drift away from.

The sample must also remain runnable without secrets or external accounts.

## Decision

Application and feature code will depend on a provider-neutral `IAIProvider` interface.

Provider-specific implementations will live behind that interface and be registered through dependency injection. Feature code must not reference a vendor SDK directly.

The initial implementation will use a deterministic local provider so the repository remains runnable without credentials. Adding a real vendor adapter later is allowed, but changing the provider-independence constraint requires a new ADR that supersedes this decision.

## Consequences

- Feature behavior is separated from provider integration details.
- A future provider can be added without changing the summarization endpoint contract.
- The repository gains an explicit architectural invariant that agents can discover before modifying code.
- The sample carries a small amount of abstraction that a one-off demo would not otherwise require.
- Provider-specific capabilities are intentionally unavailable to feature code unless promoted into the provider-neutral contract.

## Alternatives considered

### Call a vendor SDK directly from the endpoint

This is simpler initially but makes the provider choice an implicit architectural commitment and weakens the DaD example.

### Use a general-purpose HTTP client without a provider abstraction

This avoids SDK coupling but still leaves provider semantics mixed with application behavior.

### Implement multiple providers immediately

This would demonstrate replaceability but adds complexity that is not needed to establish the decision. One local provider is enough to verify the boundary.
